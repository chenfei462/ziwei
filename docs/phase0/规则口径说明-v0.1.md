# 规则口径说明 v0.1

项目：紫微斗数互动项目  
阶段：阶段 0「立项与校准」  
版本：v0.1  
日期：2026-04-30

## 1. 目的

本文冻结阶段 1「排盘引擎」的默认计算口径和可配置项。实现时不得把派别差异写死在代码里；所有可能存在口径差异的规则都应保留配置字段、测试样例和顾问备注。

## 2. 默认规则口径

| 规则项 | v0.1 默认值 | 可配置性 | 说明 |
| --- | --- | --- | --- |
| 产品口径 | Web MVP 单一默认派别 | 可配置 | 阶段 1 先实现一套默认口径，多派别插件暂缓 |
| 日历输入 | 支持公历与农历 | 必须可配置 | 输入保留 `calendar_type`，农历输入保留 `is_leap_month` |
| 时间输入 | 采用用户输入的本地出生时间 | 必须保留原始值 | 不覆盖用户原始出生时间 |
| 时区 | 必填，默认使用出生地当前/指定时区 | 必须可配置 | API 使用 `timezone` 或 UTC offset，阶段 1 不做复杂历史时区库 |
| 真太阳时 | 默认关闭 | 必须可配置 | 字段保留，启用时需要经纬度和换算说明 |
| 子时边界 | 默认按民用日期 00:00 换日 | 必须可配置 | 另保留 `zi_hour_day_boundary` 以支持晚子时口径 |
| 闰月处理 | 默认闰月按同月序参与基础计算，并记录 `is_leap_month` | 必须可配置 | 顾问可在样例盘中标注改用上一月/下一月口径 |
| 传统算法性别字段 | 必填但可选择不透露 | 必须可配置 | UI 显示为「传统算法字段」，避免身份判断 |
| 命身宫 | 按出生月与时辰确定 | 必须测试 | 需用样例盘覆盖月、时边界 |
| 十二宫 | 命、兄弟、夫妻、子女、财帛、疾厄、迁移、仆役、官禄、田宅、福德、父母 | 固定 | 宫位顺序和地支位置必须可追踪 |
| 星曜范围 | 十四主星 + 主要辅曜 + 四化 | 可扩展 | 阶段 1 不实现全量流曜 |
| 大限 | 阶段 1 只输出大限区间与对应宫位 | 可扩展 | 不输出绝对事件预测 |

## 3. 阶段 1 排盘范围

### 必须实现

- 阴阳历输入归一化，保留原始输入和中间结果。
- 安命宫、安身宫。
- 安十二宫。
- 起五行局所需的中间字段。
- 定十四主星。
- 安主要辅曜：左辅、右弼、文昌、文曲、天魁、天钺、禄存、天马、擎羊、陀罗、火星、铃星。
- 安四化：化禄、化权、化科、化忌。
- 计算大限区间和大限宫位。
- 输出可供前端渲染的 `Chart`、`Palace`、`Star`、`Transform`、`MajorPeriod` 结构。

### 暂不实现

- 流月、流日、流时。
- 多派别完整切换。
- 合盘与对照盘。
- 完整格局扫描。
- PDF/DOCX 报告生成。
- 基于视频帧的服务端手势识别。

## 4. 配置键建议

| 配置键 | 类型 | 默认值 | 用途 |
| --- | --- | --- | --- |
| `school_id` | string | `default_ziwei_v0_1` | 标记采用的排盘口径 |
| `calendar_type` | enum | `gregorian` | `gregorian` 或 `lunar` |
| `is_leap_month` | boolean | `false` | 农历输入是否闰月 |
| `timezone` | string | 用户选择 | IANA 时区或 UTC offset |
| `true_solar_time_enabled` | boolean | `false` | 是否启用真太阳时 |
| `zi_hour_day_boundary` | enum | `civil_midnight` | 支持后续切换晚子时口径 |
| `leap_month_policy` | enum | `same_month_number` | 支持后续顾问调整 |
| `gender_rule` | enum | `traditional_unspecified` | 传统算法字段 |
| `interpretation_style` | enum | `professional` | `professional` 或 `entertainment` |

## 5. 结果结构要求

排盘引擎必须输出可追踪结果，不能只返回最终文案：

- 每个宫位必须包含：地支、宫名、宫干、主星、辅曜、四化、强弱字段占位。
- 每颗星曜必须包含：名称、类别、落宫、亮度/庙旺陷字段占位、标签。
- 每条四化必须包含：化曜、类型、来源天干、作用宫位。
- 每个大限必须包含：起止年龄、对应宫位、顺逆方向字段。
- 每个中间计算步骤必须能被测试日志记录，便于顾问回查。

## 6. 样例盘验收要求

`data/phase0/sample-charts-v0.1.csv` 是阶段 1 的测试入口。进入阶段 1 前，每条样例盘必须完成：

- 顾问填写预期命宫、身宫、十二宫地支。
- 顾问填写预期十四主星落宫。
- 顾问填写预期四化结果。
- 顾问填写预期大限顺逆和区间。
- 算法工程师把顾问结果转为可解析 JSON。
- QA 标记该案例是否进入自动化断言集。

## 7. 文案规则口径

解读引擎不得单星断事。每条文案必须按以下顺序组织依据：

1. 宫位主题。
2. 星曜象义。
3. 强弱修正。
4. 三方四正、本对合邻关系。
5. 格局或限运叠加。
6. 安全改写与置信等级。

输出结构固定为：

- `basis`：依据。
- `interpretation`：现代解释。
- `scenario`：可验证的生活场景。
- `advice`：建议式行动。
- `confidence`：`strong_structure`、`medium_structure`、`weak_structure`。
- `safety_flags`：敏感主题与降级策略。

## 8. 顾问确认点

以下问题必须在阶段 0 评审时签字确认，不能留到阶段 1 临时决定：

- 默认子时换日口径是否接受 `civil_midnight`。
- 闰月默认按同月序处理是否接受。
- 大限顺逆是否依赖传统算法性别字段与阴阳年组合。
- 主要辅曜清单是否足以支持 MVP。
- 六宫解读是否按命、官禄、财帛、夫妻、福德、迁移优先。
