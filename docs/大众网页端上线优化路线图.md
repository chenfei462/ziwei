# 大众网页端上线优化路线图

## 背景

当前项目已经具备 Next.js 页面、API routes、交互命盘、解读、分享、会员、支付、小程序和运营面板等多个阶段性交付物。但整体形态仍偏向“演示原型 + 阶段验证集合”，并不等同于可直接面向大众长期使用的生产级网页产品。

上线前的重点不是继续堆功能，而是先把产品主流程、数据持久化、隐私安全、支付闭环和生产运维补齐。

## 总体目标

将项目从阶段演示系统收敛为一个稳定、可信、可运营的网页端产品：

- 用户可以顺畅完成建盘、查看解读、保存和分享。
- 用户数据、命盘、订单、权益和反馈可以持久保存。
- 出生资料等敏感信息得到明确保护。
- 付费链路真实可用，订单和权益状态可靠。
- 产品文案和合规边界适合大众传播。
- 部署、监控、测试和回滚能力满足公开服务要求。

## 最高优先级优化

### 1. 从演示原型改成真实产品入口

当前首页仍使用固定演示资料，多个页面以 `phase` 阶段形式存在，更适合内部验收和演示。

需要重构为大众可理解的产品路径：

```text
首页 -> 创建命盘 -> 查看解读 -> 保存/分享 -> 付费报告/会员权益
```

建议：

- 重做首页和主导航，隐藏阶段演示页。
- 将 `/phase7`、`/phase8`、`/phase15` 等阶段页面迁移到内部路径，例如 `/internal/phases/*`。
- 首页不要默认展示演示用户命盘，而是引导用户创建自己的命盘。
- 保留演示能力，但只用于运营、销售或测试环境。

### 2. 接入真实数据库

当前项目中大量状态仍由内存 `Map` 管理，服务重启后数据会丢失，不适合生产。

需要持久化的数据包括：

- 用户账号与匿名访客。
- 出生资料和命盘。
- 解读结果和报告草稿。
- 分享链接和分享快照。
- 订单、支付事件和会员权益。
- 用户反馈、客服工单和运营事件。

建议数据库选型：

- PostgreSQL + Prisma/Drizzle。
- Supabase 或 Neon 作为托管 PostgreSQL。
- 如果部署在 Vercel，可优先考虑 Vercel Postgres 或 Neon。

### 3. 账号、权限与隐私

紫微类产品会处理出生日期、出生时间、出生地点、性别规则等敏感资料。公开上线必须先建立清晰的数据边界。

必须补齐：

- 登录体系。
- 匿名用户升级为正式账号。
- 用户只能访问自己的命盘、报告、订单和权益。
- 分享页默认隐藏完整出生资料。
- 用户可删除自己的数据。
- 隐私政策和用户协议。
- 服务端权限校验，不能只依赖前端隐藏。

### 4. 支付链路生产化

项目已有订单、checkout、webhook、权益等模块雏形，但公开收费前必须接入真实支付能力。

需要补齐：

- 真实支付 provider。
- checkout session 创建。
- webhook 签名校验。
- webhook 幂等处理。
- 订单状态机。
- 支付成功后的权益发放。
- 退款、客服备注和异常订单处理。
- 支付失败、取消、超时等边界状态。

支付相关接口必须有自动化测试和端到端验证。

### 5. 内容可信度与合规表达

当前规则表、样例盘和解读规则仍处于工程验证阶段，不能直接宣传为专家完整验收。

上线建议定位：

- 娱乐工具。
- 自我观察工具。
- 传统文化互动体验。

需要避免：

- 医疗诊断。
- 投资建议。
- 婚恋成败判断。
- 灾祸预测。
- 绝对化人生结论。

所有解读建议保留“仅供参考”“非专业决策依据”等提示，并对高风险内容做过滤。

### 6. 生产部署与安全

需要从本地原型运行升级为可持续运行的生产服务。

必须补齐：

- 环境变量管理。
- API 输入校验。
- API rate limit。
- 统一错误返回格式。
- 日志和监控。
- 异常告警。
- 数据备份。
- CI/CD。
- 构建和测试门禁。
- 生产、预览、开发环境隔离。

生产部署应优先使用 Next.js 标准部署路径，避免依赖简单 Node HTTP server 作为公开服务入口。

## 产品体验优化

### 信息架构

建议将正式用户路径收敛为：

```text
/                 首页
/chart/new        创建命盘
/chart/[id]       命盘与解读
/report/[id]      报告详情
/share/[id]       对外分享页
/member           会员中心
/orders           订单记录
```

内部演示和运营路径可以放在：

```text
/internal/phases/*
/internal/ops
/internal/debug
```

### 建盘体验

建盘表单应简化并解释关键选项：

- 出生日期。
- 出生时间。
- 出生地点。
- 性别规则。
- 是否启用真太阳时。
- 农历/公历选择。

需要增加：

- 表单校验。
- 出生时间未知的降级说明。
- 地点搜索或城市选择。
- 移动端输入优化。

### 解读体验

解读页面应分层展示：

- 总览摘要。
- 十二宫详情。
- 重点宫位。
- 规则来源。
- 可信度或置信提示。
- 可分享内容。
- 付费报告入口。

避免一上来展示过多复杂信息，降低大众用户理解门槛。

### 移动端优先

大众用户很可能通过微信、短视频、社群或分享链接访问，移动端体验应优先于桌面端。

重点检查：

- 首屏加载速度。
- 表单输入体验。
- 命盘在小屏下的可读性。
- 分享页样式。
- 支付页跳转。
- 微信内置浏览器兼容性。

### 文案和品牌

需要将内部阶段文案替换为面向用户的正式表达。

建议：

- 移除“阶段”“demo”“演示用户”等内部词。
- 修复乱码中文内容。
- 统一产品名称、页面标题和描述。
- 明确娱乐和参考边界。
- 为分享卡、报告页、会员页统一视觉和语气。

## 工程优化

### 代码结构

建议将演示功能和生产功能分离：

```text
src/app/(public)       正式用户页面
src/app/(internal)     内部演示、运营和调试页面
src/server             业务服务层
src/repositories       数据访问层
src/lib                通用工具
src/components         可复用 UI
```

### 数据访问层

将当前内存 store 替换为数据库 repository：

- `UserRepository`
- `ChartRepository`
- `ReportRepository`
- `OrderRepository`
- `EntitlementRepository`
- `FeedbackRepository`
- `ShareRepository`

这样可以避免 API route 直接操作存储细节，后续也方便测试和迁移。

### API 标准化

所有 API 建议统一：

- 请求参数校验。
- 鉴权和权限校验。
- 错误码。
- 响应格式。
- 日志上下文。
- 幂等键。
- 速率限制。

### 测试体系

保留现有单元测试和组件测试，同时补齐生产主流程端到端测试：

- 创建命盘。
- 查看解读。
- 登录。
- 保存命盘。
- 创建分享。
- 创建订单。
- 支付 webhook。
- 权益发放。
- 访问付费报告。

CI 中至少运行：

```bash
npm run typecheck
npm test
npm run build
```

关键路径稳定后再加入 Playwright e2e。

## 运营与增长优化

### 数据指标

上线后至少需要统计：

- 首页访问量。
- 建盘开始率。
- 建盘完成率。
- 解读页停留时长。
- 分享率。
- 注册转化率。
- 付费转化率。
- 支付失败率。
- 退款率。
- 留存率。

### 客服与反馈

需要准备：

- FAQ。
- 反馈入口。
- 订单问题处理流程。
- 退款规则。
- 内容争议处理流程。
- 隐私数据删除流程。

### SEO 与分享

需要补齐：

- 页面 metadata。
- Open Graph 图片。
- 微信分享卡片。
- robots 和 sitemap。
- 结构化标题。
- 可公开索引的介绍页和内容页。

## 推荐实施路线

### 阶段 1：收敛 MVP

目标：让产品看起来像一个真正的网页产品，而不是阶段演示集合。

任务：

- 重做首页。
- 建立正式建盘流程。
- 建立正式解读页。
- 隐藏或迁移阶段演示页。
- 修复乱码文案和 metadata。
- 梳理用户主流程。

验收标准：

- 新用户可以从首页完成一次建盘和解读。
- 页面中不再出现明显内部演示文案。
- 移动端主流程可用。

### 阶段 2：生产基础

目标：让服务具备公开运行的基本可靠性。

任务：

- 接入数据库。
- 建立用户和匿名访客模型。
- 增加鉴权和权限校验。
- 接入日志、监控和错误处理。
- 增加 API rate limit。
- 建立 CI/CD。
- 增加生产环境变量管理。

验收标准：

- 服务重启后用户数据不丢失。
- 用户只能访问自己的数据。
- 关键 API 有校验、鉴权和错误处理。
- 部署流程可重复执行。

### 阶段 3：商业化闭环

目标：让付费报告和会员权益真实可用。

任务：

- 接入真实支付 provider。
- 完成订单状态机。
- 完成 webhook 签名校验和幂等处理。
- 完成权益发放。
- 完成订单后台和客服处理。
- 完成退款流程。

验收标准：

- 用户可以真实完成支付。
- 支付成功后自动获得权益。
- 重复 webhook 不会重复发放权益。
- 异常订单可以在后台处理。

### 阶段 4：增长与渠道

目标：在稳定基础上扩大获客和传播。

任务：

- 优化分享页。
- 完成 PWA。
- 完成微信内访问体验。
- 完成渠道归因。
- 完成运营看板。
- 再推进小程序适配。

验收标准：

- 分享链路可追踪。
- 渠道转化可分析。
- 移动端和微信内体验稳定。

## 关键风险

### 数据隐私风险

出生资料属于高度敏感信息。任何分享、日志、错误上报、运营导出都必须避免泄露完整出生资料。

### 内容合规风险

命理解读不能包装为确定性结论或专业建议。高风险领域必须避免直接判断。

### 支付一致性风险

订单、支付事件、权益发放必须保证幂等和可追踪，否则会产生用户投诉和财务问题。

### 范围膨胀风险

当前项目功能面很宽。公开上线前应先收敛主流程，不建议同时推进 AR、大屏、小程序、社区、报告、支付和运营后台。

## 下一步建议

优先执行“阶段 1：收敛 MVP”。先把大众用户第一次访问的完整体验打通，再进入数据库、账号和支付等生产化工作。

第一批可拆任务：

1. 重做正式首页。
2. 新增 `/chart/new` 建盘页。
3. 新增 `/chart/[id]` 解读页。
4. 将阶段页面迁移到 `/internal/phases/*`。
5. 修复乱码中文和页面 metadata。
6. 梳理正式产品文案和免责声明。
