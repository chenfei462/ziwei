# 大众网页端正式交付产品优化清单

## 定位说明

本文档不按 MVP 标准编写，而按“完成后可以直接交付给大众用户使用”的正式产品标准整理。

当前项目已经具备 Next.js 页面、交互命盘、解读、分享、会员、支付、小程序、运营面板等功能雏形，但整体仍偏向阶段演示和内部验证。要成为可公开上线、可收费、可长期运营的网页端产品，需要完成产品化、生产化、商业化、合规化和运维化升级。

## 交付目标

最终产品应满足以下目标：

- 大众用户可以从首页完整完成建盘、解读、保存、分享和查看报告。
- 用户数据、命盘、报告、订单、权益和反馈可以长期保存。
- 用户只能访问自己的私密数据。
- 分享页不会泄露完整出生资料。
- 支付、订单、报告和会员权益形成真实闭环。
- 后台可以处理用户、订单、退款、客服和权益问题。
- 移动端体验稳定，适合微信、社群、短视频等传播场景。
- 有隐私政策、用户协议、免责声明和内容合规边界。
- 有测试、监控、日志、备份、部署和回滚能力。

## 一、产品主流程优化

正式产品不能让用户看到阶段页面、演示用户、测试账号或内部验收文案。

需要建立清晰的大众用户路径：

```text
首页
注册 / 登录 / 匿名体验
创建命盘
查看完整解读
保存命盘
生成报告
分享页面
会员中心
订单中心
客服与反馈
```

建议正式路由：

```text
/                  首页
/chart/new         创建命盘
/chart/[id]        命盘与解读
/report/[id]       报告详情
/share/[id]        对外分享页
/member            会员中心
/orders            订单中心
/support           客服与反馈
/legal/privacy     隐私政策
/legal/terms       用户协议
```

内部演示、阶段验收和运营调试页面应迁移到内部路径：

```text
/internal/phases/*
/internal/ops
/internal/debug
```

## 二、正式账号与用户体系

公开产品必须有真实用户体系，不能依赖固定 `member_id`、演示账号或纯前端状态。

必须支持：

- 手机号、邮箱或微信登录，至少一种正式登录方式。
- 匿名用户先体验，后续可升级为正式账号。
- 用户资料管理。
- 命盘列表。
- 报告列表。
- 订单列表。
- 会员权益列表。
- 用户数据删除或删除申请入口。
- 服务端权限校验。

权限规则：

- 用户只能查看自己的命盘、报告、订单和权益。
- 分享页只能展示被允许公开的信息。
- 管理后台必须有管理员权限。
- 前端隐藏不能替代后端鉴权。

## 三、数据库与后端生产化

当前项目如果仍依赖内存 `Map`，则不能直接交付。生产环境必须接入真实数据库和稳定的数据访问层。

建议技术方案：

- PostgreSQL 作为主数据库。
- Prisma 或 Drizzle 作为 ORM / schema 管理工具。
- Redis 用于缓存、限流、短期 session 和幂等键。
- 对象存储用于报告文件、分享图片、导出文件。

核心数据模型至少包括：

- 用户。
- 匿名访客。
- 出生资料。
- 命盘。
- 解读结果。
- 报告。
- 分享链接。
- 订单。
- 支付事件。
- 会员权益。
- 反馈。
- 客服工单。
- 运营事件。
- 管理员账号和操作日志。

后端接口必须统一：

- 请求参数校验。
- 鉴权。
- 权限校验。
- 错误码。
- 响应格式。
- 日志上下文。
- 速率限制。
- 幂等处理。

## 四、命盘与解读质量优化

大众用户最关心的是“算得准、说得稳、看得懂”。正式交付前必须提升规则可信度和内容表达质量。

需要完成：

- 排盘结果与可信第三方库或专家样例交叉校验。
- 建立专家审核样例库。
- 建立 golden tests。
- 对十二宫、主星、四化、大限、流年等关键结果做稳定测试。
- 解读规则由顾问确认，不能只停留在工程规则表。
- 解读内容按置信度分层。
- 标注规则来源。
- 对出生时间未知、地点未知、时区异常等情况提供降级说明。

内容表达要求：

- 避免绝对化断言。
- 避免制造焦虑。
- 避免医疗、投资、婚恋成败、灾祸预测等高风险判断。
- 明确说明结果仅供娱乐、自我观察和传统文化体验参考。

## 五、隐私与合规

出生日期、出生时间、出生地点、性别规则等属于敏感信息，必须按高隐私标准处理。

必须补齐：

- 隐私政策。
- 用户协议。
- 免责声明。
- 数据删除机制。
- 分享页脱敏机制。
- 日志脱敏。
- 错误上报脱敏。
- 后台导出脱敏。
- 敏感字段访问控制。
- 必要时对敏感字段加密存储。

分享页默认不得展示：

- 完整出生日期。
- 完整出生时间。
- 精确出生地点。
- 用户真实姓名或可识别身份信息。

公开文案必须避免：

- 医疗建议。
- 投资建议。
- 法律建议。
- 婚恋成败判断。
- 灾祸预测。
- 绝对命运判断。

## 六、支付和会员闭环

如果产品包含收费报告或会员权益，支付链路必须达到生产级。

必须完成：

- 真实支付 provider 接入。
- checkout session 创建。
- webhook 签名校验。
- webhook 幂等处理。
- 订单状态机。
- 支付成功后的权益发放。
- 支付失败、取消、超时处理。
- 退款流程。
- 客服备注。
- 权益补发。
- 权益过期和续费处理。
- 支付异常告警。

订单状态至少覆盖：

```text
created
pending_payment
paid
failed
cancelled
refunded
partially_refunded
fulfilled
```

支付事件必须可追踪，重复 webhook 不得重复发放权益。

## 七、正式报告系统

正式产品不能只有一次性页面解读，还需要可保存、可复看、可分享、可付费的报告体系。

报告系统需要支持：

- 报告生成。
- 报告版本管理。
- 免费版和付费版区分。
- 报告访问权限。
- 报告分享摘要页。
- 私密报告详情页。
- PDF 或长图导出。
- 报告生成失败重试。
- 报告内容审核。
- 报告购买后的权益校验。

报告页应包含：

- 总览摘要。
- 核心主题。
- 十二宫细节。
- 重点提示。
- 规则来源。
- 免责声明。
- 保存、分享和导出入口。

## 八、后台管理系统

可交付产品必须有后台，否则上线后无法处理真实用户问题。

后台至少包括：

- 用户管理。
- 命盘查询。
- 报告查询。
- 订单管理。
- 支付事件查看。
- 退款处理。
- 权益补发。
- 客服工单。
- 反馈管理。
- 内容规则配置。
- 分享与渠道数据。
- 系统日志。
- 异常记录。
- 管理员操作审计。

后台安全要求：

- 只有管理员可访问。
- 管理员权限分级。
- 关键操作写入审计日志。
- 敏感字段默认脱敏。
- 不允许通过公开导航进入后台。

## 九、性能与稳定性

正式交付需要考虑真实流量、移动端网络和异常场景。

需要优化：

- 首页首屏加载。
- 建盘接口响应时间。
- 解读接口缓存。
- 分享页静态化或缓存。
- 图片优化。
- API 超时控制。
- 错误边界。
- 404 和 500 页面。
- 数据库索引。
- 限流和防刷。
- 异常告警。
- 降级体验。

交付标准：

- 服务重启后数据不丢失。
- 核心 API 有清晰错误提示。
- 单个用户重复提交不会产生脏数据。
- 支付 webhook 重放不会重复发权益。
- 移动端核心路径稳定可用。

## 十、安全要求

正式产品必须补齐基础 Web 安全能力。

必须包括：

- API 参数校验。
- 鉴权中间件。
- 权限校验。
- CSRF 或来源校验。
- XSS 防护。
- SQL 注入防护。
- Rate limit。
- Bot 防护。
- 管理后台权限控制。
- 环境变量隔离。
- 密钥不得进入 Git。
- 支付 webhook 签名校验。
- 文件上传安全策略。

## 十一、测试与验收

交付产品必须有覆盖关键路径的自动化测试。

必须覆盖：

- 建盘流程。
- 解读流程。
- 登录流程。
- 匿名用户升级。
- 保存命盘。
- 创建分享。
- 查看分享页。
- 查看报告。
- 创建订单。
- 支付成功。
- 支付失败。
- 权益发放。
- 退款。
- 用户无权访问他人数据。
- 移动端核心路径。

CI 至少运行：

```bash
npm run typecheck
npm test
npm run build
npm run test:e2e
```

若 e2e 成本较高，至少要保证核心公开路径每日或每次发布前运行。

## 十二、部署与运维

正式交付必须具备可重复部署和可恢复能力。

需要补齐：

- 生产环境。
- 预发环境。
- 开发环境。
- 数据库迁移流程。
- 环境变量文档。
- 自动部署。
- 回滚方案。
- 日志平台。
- 错误监控。
- 性能监控。
- 数据备份。
- 域名。
- HTTPS。
- CDN。
- robots。
- sitemap。

部署文档至少说明：

- 如何安装依赖。
- 如何配置环境变量。
- 如何执行数据库迁移。
- 如何启动开发环境。
- 如何构建生产版本。
- 如何部署。
- 如何回滚。
- 如何恢复备份。

## 十三、增长与传播

大众产品需要完整传播链路，而不仅是功能页面。

需要支持：

- SEO 页面。
- Open Graph 分享图。
- 微信分享适配。
- 分享短链。
- 渠道参数。
- 邀请记录。
- 用户来源统计。
- 转化漏斗。
- 留存分析。
- 付费转化分析。

关键指标：

- 首页访问量。
- 建盘开始率。
- 建盘完成率。
- 解读页停留时长。
- 分享率。
- 注册转化率。
- 付费转化率。
- 支付失败率。
- 退款率。
- 留存率。

## 十四、正式交付验收标准

满足以下条件，才可认为项目达到“可直接交付给大众使用”的标准：

- 用户可以从首页完整完成建盘、解读、保存、分享和查看报告。
- 用户数据持久保存，服务重启不丢失。
- 用户只能访问自己的私密内容。
- 分享页不会泄露完整出生资料。
- 支付、订单、报告和权益真实闭环。
- 后台可以处理订单、退款、客服和权益问题。
- 移动端体验稳定。
- 生产构建通过。
- 自动化测试通过。
- 有隐私政策、用户协议和免责声明。
- 有监控、日志、备份和回滚方案。
- 没有公开暴露 demo、phase、测试账号和内部运营入口。
- 内容表达符合娱乐、自我观察和传统文化体验定位。

## 推荐实施顺序

### 第一阶段：产品主流程重构

- 重做首页。
- 建立正式建盘页。
- 建立正式解读页。
- 建立正式报告页。
- 建立分享页。
- 建立会员中心和订单中心。
- 隐藏或迁移阶段演示页。
- 修复乱码、metadata 和内部文案。

### 第二阶段：生产数据与账号体系

- 接入数据库。
- 建立 repository/service 层。
- 建立用户和匿名访客模型。
- 增加登录。
- 增加权限校验。
- 增加数据删除能力。
- 增加隐私和协议页面。

### 第三阶段：支付、报告和权益闭环

- 接入真实支付。
- 完成订单状态机。
- 完成 webhook 幂等。
- 完成权益发放。
- 完成报告权限控制。
- 完成退款和客服流程。

### 第四阶段：后台、测试和运维

- 建立管理后台。
- 补齐 e2e 测试。
- 建立 CI/CD。
- 接入日志、监控和告警。
- 完成备份和回滚方案。
- 完成部署文档。

### 第五阶段：增长和渠道

- 优化 SEO。
- 优化分享图。
- 接入渠道归因。
- 建立转化漏斗。
- 建立运营看板。

## 总结

这个项目要成为可直接交付的网页端产品，不能停留在“功能能演示”的层面。它需要升级为一个有账号、有数据、有隐私保护、有支付闭环、有报告体系、有后台、有测试、有监控、有部署方案的正式互联网产品。

优先级应是：先稳定大众主流程，再补生产数据和账号体系，然后完成支付、报告、后台和运维能力，最后再推进增长和渠道能力。
