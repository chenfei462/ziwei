### C-5 攻击链（含一条必须澄清的精确区分）

**【已确认事实】三条 provider 路径的安全等级并不一致**：
- `wechat_pay_reserved`：**fail-closed** —— `commerce.ts:862-865` 无 `WECHAT_PAY_PLATFORM_CERT` 即抛错，另校验平台证书序列号与 5 分钟时效（实现正确）。
- `alipay_reserved`：走 RSA2 验签。
- `stripe_checkout` / `mock_checkout`：**回退到源码公开常量**（`commerce.ts:37-38`、`:951`、`:984`）。

**而 `stripe_checkout` 恰是 webhook 的默认 provider**（`route.ts:50`）。因此攻击链为：
1. 正常下单，获得 `checkout_session_id`；
2. 向 `/api/payment/webhook?provider=stripe_checkout` POST 伪造的 `checkout.session.completed` 事件；
3. 自行用公开常量 `phase9_sandbox_webhook_secret` 计算合法 HMAC 签名（`commerce.ts:826` 用的正是该密钥）；
4. `applyPaymentEvent`（`commerce.ts:614-629`）无状态机守卫，直接置订单 `fulfilled` 并 `grantEntitlement`；
5. → **零成本获得付费报告权益**。

> **必须避免的过度结论**：不应得出"支付验签整体不可信"。真实问题是**默认值与可选 provider 的组合**，不是算法实现。

**另附一个独立的完整性缺陷【已确认事实】**：`applyPaymentEvent:631-639` 的 `checkout.session.canceled` 会**无条件**把已 `fulfilled` 的订单覆写为 `cancelled`，且**不回收已发放的权益** → 乱序或重放事件即可造成"订单已取消但权益仍在"的不一致。

## 4. 隔离与止损措施 + 恢复步骤（四阶段）

### 阶段一 · 立即止损（0–30 分钟，无需改代码）

| 动作 | 生效速度 | 副作用 |
|------|---------|--------|
| 注入真实 `PHASE10_ADMIN_TOKEN`（≥24 字符）并开启 MFA | 分钟级 | 无 |
| 网关层**封禁 `/api/ops/*` 外网直连**（仅内网/VPN） | 分钟级 | 后台需经内网访问 |
| 注入真实 `SESSION_SECRET`（≥24 字符） | 分钟级 | 已签发 cookie 失效，用户需重登 |
| 注入真实 `STRIPE_WEBHOOK_SECRET`；**或**临时在网关只放行真实支付 provider 的回调源 IP | 分钟级 | 测试回调可能被拦 |
| 置 `ZIWEI_RATE_LIMIT_REDIS_REQUIRED=true` 并配置 Redis | 分钟级 | 未配 Redis 时写接口将失败关闭 |
| 轮换 DeepSeek 等第三方 Key | 分钟级 | 无 |

**验收标准**：伪造默认令牌访问 `/api/ops/*` 返回 401；伪造 webhook 返回 `PAYMENT_WEBHOOK_SIGNATURE_INVALID`；`/api/ops/*` 外网不可达。

### 阶段二 · 修复（小时级，需改代码）

1. 移除**所有** `process.env.X || 固定常量` 回退（`launchOps.ts:144`、`commerce.ts:37-38/951/961/973/984`）。
2. 环境变量缺失时**启动即失败**（fail-closed），而非运行时静默降级。
3. webhook **provider 强白名单**，禁止客户端指定；校验 `provider_mode`。
4. `applyPaymentEvent` 引入**状态机 + 幂等键** + 乱序守卫 + 权益回收。
5. 移除 `auth.ts` 的未签名 cookie 回退（`readSessionCookieValue` / `signSessionCookieValue`）。
6. `assertCanReadChart` 的 `!owner` 分支改抛 403。
7. 角色/actor 改由服务端会话确定，废弃 `x-admin-role` 头信任。

**验收标准**：新增的 fail-closed 负向单测全部通过；`npm run typecheck` 零错误。

### 阶段三 · 验证（天级）

CI 接入并扩门禁至全量测试；对账跑通（`ops/reconciliation` 无 `entitlement_gap`）；补 §7 的生产排查。

**验收标准**：CI 全绿；对账无权益缺口；`audit_logs` 无异常 actor。

### 阶段四 · 恢复放量

`PHASE10_PAYMENT_ROLLOUT_PERCENT` 按 1 → 10 → 50 → 100 逐级放量，每级观测支付成功率、5xx、验签失败率。

**验收标准**：各级指标达标；kill 开关验证可即时回滚。

### 根因分析 · 5 Why（以 C-6 为主链，最强）

1. **为什么外部能进入管理后台？** → 未设 `PHASE10_ADMIN_TOKEN` 时使用硬编码默认令牌（`launchOps.ts:1277`）。
2. **为什么存在这个默认值？** → `env || default` 模式让本地开发免配置即可跑通。
3. **为什么它能进入生产？** → 没有 `NODE_ENV=production` 硬失败，也没有启动期强校验。
4. **为什么发布前没拦住？** → 无 CI、无密钥扫描；`verify:public` 只跑 6 个测试文件，从不断言"生产必需环境变量"。
5. **为什么这些都没拦？** → **【系统性根因】缺失部署流水线与 Go/No-Go 强制执行机制，安全配置停留在"readiness JSON 文档级"，而非"启动即 fail-closed"的运行时护栏。**

> 该根因同时解释了 C-5（webhook 密钥回退）与 C-1（会话密钥回退）——**同一个模式在三个模块重复出现，说明这不是疏忽，而是缺少护栏的系统性问题。** 这一点决定了修复策略必须是"加护栏 + 加负向测试"，而非逐处打补丁。

## 6. 可观测性与预防措施

### 能否发现？—— **当前不能**

**【已确认事实】** `evaluateOperationalAlerts` 与 `formatStructuredLog`（`observability.ts:95,112`）**从不被调用**：无日志 emit、无告警推送。因此 C-5 / C-6 若已被利用，**只能靠用户被动投诉发现，MTTD ≈ ∞**。

**已有基础（不必从零造）**：未授权访问计数 `recordUnauthorizedOpsAccess`（`store.ts:583`）已存在计数能力，缺的是**上报与告警**。

### 最小可行检测方案

1. 把 `formatStructuredLog` 推送至 `OBS_LOG_SINK`；
2. 定时调用 `evaluateOperationalAlerts` 并 POST 至 `OBS_ALERT_WEBHOOK_URL`。

### 最小告警集（含所需字段）

| # | 告警 | 判据 | 数据来源 |
|---|------|------|---------|
